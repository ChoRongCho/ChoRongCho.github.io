2-4. Plan Space

마지막 업데이트: 2026-08-22

From State Space to Plan Space

State-space planning에서는 하나의 state를 search node로 사용하고, action을 적용하여 다음 state를 생성했습니다. 반면 plan-space planning에서는 아직 완성되지 않은 partial plan 자체가 하나의 search node가 됩니다. 즉, “현재 world가 어떤 state인가?”를 탐색하는 대신 “현재 plan에서 부족하거나 잘못된 부분은 무엇인가?”를 찾아 plan을 조금씩 수정합니다. 그래서 plan-space planning을 plan refinement planning이라고 부르기도 합니다.

State-space planning이 매 순간 실행할 action을 순서대로 선택한다면, plan-space planning은 goal을 달성하는 데 필요한 action과 그 action 사이의 관계를 먼저 선택합니다. 서로 순서가 상관없는 action은 굳이 어느 action이 먼저인지 정하지 않습니다. 이러한 원칙을 least commitment라고 부릅니다.

Partial-Order Plan

가장 기본적인 partial-order plan은 다음과 같이 표현할 수 있습니다.

\[ \mathcal{P}=(A,O,L) \]

  • \(A\): plan에 포함된 action 또는 step의 집합
  • \(O\): action 사이의 ordering constraint 집합
  • \(L\): action 사이의 causal link 집합

구현에 따라 variable binding constraint를 나타내는 \(B\)를 추가하여 \(\mathcal{P}=(A,O,L,B)\)로 표현하기도 합니다. 여기서는 구조를 단순하게 설명하기 위해 ground action만 사용하겠습니다.

Start and Finish

Partial plan에는 보통 두 개의 특별한 action, \(Start\)와 \(Finish\)를 둡니다. \(Start\)는 precondition이 없고 initial state \(I\)를 effect로 가집니다. 반대로 \(Finish\)는 effect가 없고 goal \(G\)를 precondition으로 가집니다. 모든 실제 action \(a\)에 대해서 다음 ordering constraint가 성립합니다.

\[ Start \prec a \prec Finish \]

처음에는 \(Start\)와 \(Finish\)만 존재합니다. 하지만 \(Finish\)의 precondition인 goal을 아직 어떤 action도 만들어 주지 않았기 때문에 이 plan은 완성된 plan이 아닙니다.

Open Condition

Plan에 포함된 action \(a_j\)의 precondition \(p\)를 보장해 주는 action이 아직 없다면, \(p\)를 open condition이라고 부릅니다. Open condition을 해결하는 방법은 다음 두 가지입니다.

  1. \(p\)를 effect로 만드는 새로운 action을 plan에 추가합니다.
  2. 이미 plan에 있는 action 중 \(p\)를 만드는 action을 재사용합니다.

어떤 action \(a_i\)가 \(p\)를 만들고, 그 fact를 action \(a_j\)가 precondition으로 사용한다면 두 action 사이에 ordering constraint \(a_i\prec a_j\)를 추가합니다. 그리고 \(a_i\)가 만든 \(p\)를 \(a_j\)가 사용할 때까지 보호해야 합니다.

Causal Link

위의 관계를 causal link라고 부르며 다음과 같이 표현합니다.

\[ a_i \xrightarrow{p} a_j \]

이는 action \(a_i\)가 fact \(p\)를 만들어 action \(a_j\)의 precondition을 support한다는 의미입니다. Causal link는 단순히 두 action의 순서를 나타내는 것보다 더 많은 정보를 가집니다. 두 action이 왜 그 순서를 가져야 하는지, 그리고 그 사이에서 어떤 fact가 계속 참이어야 하는지를 함께 표현하기 때문입니다.

Logistics Example

이전 페이지의 Logistics 문제를 다시 생각해 보겠습니다. Package를 unload하기 위해서는 package가 truck 안에 있어야 하고 truck이 location \(R\)에 있어야 합니다. Truck \(A\)를 사용한다면 partial plan에는 다음 causal link가 필요합니다.

\[ load(p,A,L) \xrightarrow{in(p,A)} unload(p,A,R) \]

\[ drive(A,L,R) \xrightarrow{at(A,R)} unload(p,A,R) \]

Package를 load하려면 먼저 truck \(A\)가 location \(L\)에 도착해야 합니다. 그리고 load 이후에는 truck을 \(R\)로 이동한 다음 package를 unload해야 합니다.

\[ drive(A,R,L) \prec load(p,A,L) \prec drive(A,L,R) \prec unload(p,A,R) \]

Threat

Causal link \(a_i \xrightarrow{p} a_j\)가 있을 때, 다른 action \(a_t\)가 \(p\)를 delete하고 \(a_i\)와 \(a_j\) 사이에 실행될 가능성이 있다면 \(a_t\)가 causal link를 threaten한다고 말합니다.

\[ p\in (a_t)_{del}, \qquad O\cup\{a_i\prec a_t\prec a_j\}\text{ is consistent} \]

예를 들어 \(drive(A,L,R)\xrightarrow{at(A,R)}unload(p,A,R)\)라는 causal link가 있다고 하겠습니다. 만약 \(drive(A,R,L)\)이 두 action 사이에 다시 실행되면 \(at(A,R)\)을 삭제하기 때문에 unload를 실행할 수 없습니다. 따라서 이 위치의 \(drive(A,R,L)\)은 causal link에 대한 threat입니다.

Threat Resolution

Threat는 ordering constraint를 추가하여 해결할 수 있습니다.

  • Promotion: threatening action을 consumer보다 뒤로 이동합니다. \(a_j\prec a_t\)
  • Demotion: threatening action을 producer보다 앞으로 이동합니다. \(a_t\prec a_i\)

Promotion이나 demotion을 추가했을 때 기존 ordering constraint와 cycle을 만들면 사용할 수 없습니다. Variable이 포함된 action에서는 두 action의 variable이 같은 object를 나타내지 못하도록 binding constraint를 추가하는 separation을 사용할 수도 있습니다.

Plan Refinement

Partial-order planner는 일반적으로 다음 과정을 반복합니다.

  1. 현재 partial plan에서 open condition 또는 threat와 같은 flaw를 하나 선택합니다.
  2. Open condition을 support할 action을 추가하거나 기존 action을 재사용합니다.
  3. 필요한 causal link와 ordering constraint를 추가합니다.
  4. 새롭게 발생한 threat를 promotion, demotion 또는 separation으로 해결합니다.
  5. Open condition과 threat가 모두 없어질 때까지 plan을 refinement합니다.

모든 precondition이 causal link로 support되고 모든 threat가 해결되었다면 partial plan은 solution을 나타냅니다. 이때 ordering constraint를 만족하는 action의 모든 total ordering을 linearization이라고 부릅니다. 올바른 partial-order plan의 linearization은 goal을 만족하는 sequential plan이 됩니다.

Total Order vs. Partial Order

Total-Order Plan Partial-Order Plan
표현 하나의 고정된 action sequence Action과 필요한 ordering constraint
독립적인 action 임의의 순서 하나를 선택 순서를 정하지 않고 유지 가능
Search node 주로 world state Incomplete partial plan
수정 대상 현재 state에서 실행할 다음 action Open condition, threat 등의 flaw

Partial-order planning의 장점은 필요한 순서만 결정하기 때문에 독립적인 subtask의 관계를 유연하게 남겨 둘 수 있다는 것입니다. 반면 search node가 action, causal link, ordering constraint를 함께 포함하므로 successor를 생성하고 중복된 plan을 판별하는 과정은 state-space search보다 복잡해질 수 있습니다. UCPOP과 VHPOP은 이러한 partial-order causal-link planning을 대표하는 planner입니다.
